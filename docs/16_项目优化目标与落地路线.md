# 项目优化目标与落地路线

日期：2026-09-06　项目：Project_03 本地短视频批量混剪工作台（智剪 / SmartCut）

## 1. 结论：先把已有能力变成可稳定交付的产品

建议近期总目标：让普通 Windows 用户安装后，可以完成“导入真实素材 → 配置 → 批量生成 → 查看成片”，中途失败能重试，取消能停下来，关闭后能恢复必要信息，整个过程不误删素材。

项目已不是空白原型。现有 Vue/Tauri/Rust/FFmpeg 架构、素材库、混剪、配音、字幕、会员、诊断和安装包基础值得保留。当前优先投入应当是成片正确性、任务可靠性、真实验收和安装交付；随后再优化维护成本、处理速度和匹配质量。

本方案遵守既定 ECutAuto 公开体验对齐方向；现有已获用户确认的主题与信息流模块继续保留。优化内部实现和可靠性，不擅自改版、删除已要求实现的功能、更换技术栈或修改数据库。需要数据库迁移、付费资源和新产品行为时另行说明影响。

**本次交付是代码阅读后的实施方案，不是功能修复或发布验收报告。下面的数值均为建议验收目标，不是已经测得的产品成绩。**

## 3. 怎样才算“可落地”

每项工作必须具备：明确的问题、负责人角色、涉及模块、依赖、可独立完成的小任务、可保存的交付物、可重复的验收方法、失败处理。

完成状态分成：**界面完成 → 参数接线完成 → 真实结果验收完成 → 可交付**。构建通过只能证明代码能编译；能点按钮不能证明成片正确；本机可用不能证明新电脑可用。

优先级定义：P0为数据丢失、权限错误或核心流程无法完成的阻断问题；P1为主要功能错误、无法可靠取消/重试或必需发布条件缺失；P2为性能、质量和维护改进。静态风险先复现再定级，不把所有建议都算作已存在的P0。

建议责任分工：开发者负责实现和自动化证据；测试者负责桌面与干净机器回归；项目负责人确认用户体验和成片质量。同一个人可以兼任，但记录要区分检查与最终验收。

## 5. G01：把当前项目状态统一成一张可执行清单

**目标：** 后续开发十分钟内知道已验收、待验收、失败和下一步分别是什么。

1. 以已有 `docs/15_发布前全局人工验收方案.html` 的44项为母表，保留项目与测试结果之间的对应关系。
2. 每项补充版本号/Git提交、输入素材、输出路径、检查时间、执行人和真实结果；历史“通过”不能自动迁移为当前版通过。
3. 把 CURRENT_TASK.md 历史内容完整移入归档文档，短入口建议控制在120行以内，仅保留一个当前任务。同步 TODO_NEXT.md 和全局状态，保留历史证据。
4. 准备可复用素材：横屏、竖屏、带旋转元数据、无音轨、中文及空格路径、损坏文件、混合分辨率/帧率。最初用短素材，性能阶段另用长素材。
5. 跑四条最短主链路：普通混剪、分类混剪、AI配音成片、信息流三版本。受账号或外部服务阻挡时标记“阻塞”，不能算通过。

涉及：CURRENT_TASK.md、TODO_NEXT.md、docs/15、TASK.md、CHANGELOG.md。预计增加 `docs/acceptance/` 功能状态表及 `tasks/` 小任务卡。

验收：44项全部有明确状态；当前任务只有一个；四条链路各有输入、输出或明确阻塞原因；失败项都有最短复现步骤。该阶段不要求所有失败都已修复，但必须可据此排期。

## 6. G02：成片正确后才能宣告成功或删除原素材

**目标：** “文件生成了”升级为“文件可用，而且对应这次任务”。

1. 先为现有保护建立基线：输出缺失、输出等于源文件、空输出列表均应拒绝删除。
2. 在统一 VideoEngine 输出边界增加成片验证：文件非空、FFprobe可读、存在视频流、时长有效、分辨率/帧率符合任务要求；应有音轨的任务检查音轨。
3. 输出先写任务临时文件，验证成功后再按既定命名发布到结果目录；处理跨盘移动、目标重名和文件被占用。失败不能覆盖已有正常成片。
4. 删除动作使用后端验证过的任务输出记录，不能只信前端传来的任意存在路径；确认本批次依赖源素材的任务全部成功后再进入既有删除规则。
5. 采用测试素材副本做破坏性故障用例；实际用户素材不用于删除测试。关键回归包含完整解码，普通批次可按性能选择分层校验。

涉及：`src-tauri/src/lib.rs`、`video_engine/output.rs`、`render.rs`、`mix.rs` 和前端 remix-export 服务。复用 probe 能力，不绕开 VideoEngine 散写处理命令。

验收：正常成片、零字节、截断成片、输出同源、输出被移走、文件占用、批次部分失败七类场景各有结果；失败和取消均不删除源素材；不同任务输出不能冒充本任务完成证明。时长容差按速度/裁切/封面计算，固定样例建议取100ms与两帧中的较大值。

失败处理：保留输入与诊断记录，清理仅属于该任务的临时文件，不把失败结果登记为成功。不以“永久隐藏删除开关”代替已要求实现的功能。

## 7. G03：批量任务随时可控，失败只重做失败部分

**目标：** 单任务、自动并发、多任务模式共享取消与真实进度能力。

1. 先复现并发取消：至少同时运行两条足够长的导出，点击取消并观察本应用启动的 FFmpeg 进程、文件写入和状态变化。
2. 把“取消信号传递”与“总体百分比计算”分开；每条并发子任务都收到取消上下文，再按已完成数量或实际处理工作量汇总进度，避免并发相互覆盖百分比。
3. 批次保存每条任务的选材、参数、目标路径和状态；重试保留原选材与参数。已有失败重试逻辑应复用，不重新随机生成另一条视频。
4. 取消后停止领取后续任务，结束本批次子进程，保留已成功输出；区分失败、取消、部分成功，按竞品已确认的界面方式呈现。
5. 为已结束的内存任务记录定义回收策略，避免长时间运行不断累积；诊断历史与运行注册表职责分开。

涉及：`useRemixGeneration.ts`、`src/features/task-center/`、`src-tauri/src/task_runtime.rs`、`video_engine/mix.rs`。

验收：单任务及2/4并发分别正常导出、取消、制造一个失败再重试；建议取消后5秒内本批次处理进程结束，无新任务启动，成功文件哈希不变，重试不重复生成成功项。该时限需先测本机基线；网络服务取消单独定义，不混为FFmpeg取消。

## 8. G04：用户配置与实际视频一致

**目标：** 每个已开放参数都有真实结果证据，预览与输出不相互矛盾。

1. 建立“控件 → 前端状态 → 请求字段 → Rust处理 → 成片检查”的参数契约表。先覆盖输出比例、裁剪、变速、字幕、水印、BGM、片头片尾、文件夹规则与信息流模板。
2. 一次改变一个参数，导出前后对照；再测高风险组合：裁剪+文字、变速+音轨、字幕+竖屏、画中画+模糊背景、文件夹规则+并发。
3. 使用共用预览尺寸与坐标换算。文字当前落到后端五个位置的实现需要与界面表达核对；如果界面承诺任意拖动位置，必须让输出具备同等位置能力，不能只让预览自由移动。
4. 对信息流模块先验证模板、人工镜头顺序、分类修正、商品字段、三版本和失败重试；区分“素材不足无法产生不同顺序”和“已成功生成不同版本”。
5. 按既有方向保留四套实际主题，检查首页、所有工作区、设置弹窗、个人中心、引导和诊断；跟随系统主题单独检查。

涉及：`PreviewPanel.vue`、`src/types/outputSettings.ts`、`src/services/videoMixService.ts`、`App.vue` 信息流编排、`CommerceRemixWorkbench.vue`、remix-export、video_engine 与 theme。

验收：参数表每个开放参数至少一个真实用例；高风险组合有额外用例；1440×900和1280×720均覆盖横竖素材，切换工具前后播放器外壳尺寸变化不超过1个CSS像素；文字、裁剪用相同坐标基准比较，建议边界误差不超过输出尺寸的1%。颜色与字体检查允许抗锯齿差异，不要求视频帧逐像素相同。

视觉检查不能只看空状态，至少覆盖导入、处理中、完成/失败；未有竞品证据的细节登记“待校准”，不猜测后宣称一致。

## 9. G05：重开软件后能继续工作

**目标：** 重启不丢配置、素材关联和已完成结果；不把恢复配置等同于续跑编码。

1. 补充恢复覆盖表：普通混剪、分类混剪、AI混剪、视频效果、信息流；逐项核对素材、参数、输出目录、成片结果与失败条目。
2. 复用现有快照格式与安全清理，先写版本兼容方案。需要增加字段时兼容旧快照，不直接覆盖不能识别的数据。
3. 强制关闭后，将原处理中任务恢复为“中断待重试”或竞品对应状态，不能显示还在真实处理。仅重做未完成条目；不承诺从某一帧继续编码。
4. 缺失素材先提示重新定位；路径恢复不能错误关联同名不同文件。保存时使用原子替换，保留可读的上一份有效快照。

涉及：project-recovery、project_snapshot.rs、task-center、App.vue信息流状态。若需要SQLite迁移，先交付迁移/回滚方案并按项目规则获得确认；该目标不预先授权改表。

验收：五类工作流至少各一次正常关闭恢复；批量任务中断、坏快照、素材移动各有测试；已成功成片不重复导出；恢复后的参数与保存前一致；密钥不进入项目快照。

## 10. G06：AI服务问题能解释，质量提升能衡量

**目标：** AI、配音、识别遇到问题时可定位、可重试，成功结果确实可用。

1. 复用已有最多三次受控重试，核对哪些错误可重试：限流、超时、暂时服务错误；无效密钥、额度不足、输入错误应提示处理办法，避免盲目反复请求。
2. 建立错误分类，保留文案和素材；请求ID与任务关联，日志脱敏。取消后不自动继续付费请求；请求可能已在远端执行时明确记录状态。
3. 检查缓存标识是否包含素材变化、模型与参数；相同条件才复用，模型或内容变化应重新计算。
4. 建立20条有人工标注的“文案—镜头”样例，评分相关性、漏句、重复镜头；配音检查无空音频、字幕时间单调递增、末句不截断。

涉及：ai-remix、tts、asr、analysisCache.ts、ai_remix.rs、tts.rs、asr.rs、api_config.rs。

验收：401/403、429、超时、5xx、无效响应、成功六类行为有可重复测试；云端实际验证与模拟响应分开记；建议首版20条中至少16条达到事先定义的人工相关性标准，未达标记录失败类型。成本和速度先测，不承诺零费用或云服务百分之百成功。

## 11. G07：文件与会员权限符合实际业务范围

**目标：** 合法素材能读，处理权限准确，敏感信息不会出现在交付物中。

1. 清点视频预览、缩略图、配音、临时文件的访问路径，按用户选中文件夹与应用缓存目录授予范围，替换全盘 `**/*` 的宽范围配置。先验证动态目录支持方式，避免直接改配置导致所有预览失效。
2. 核验前端执行门禁与Rust/服务端执行边界，覆盖未登录、未激活、过期、有效、设备不符和断网。前端按钮禁用不能代替需要的后端校验。
3. 复用Windows加密缓存和远程签名验证，不改成本地无条件通过；运行会员服务已有测试，再核对真实配置下行为。
4. 检查诊断、错误提示、快照和安装包不含API密钥及管理员凭据。日志只记录必要的脱敏信息。

涉及：tauri.conf.json、capabilities/default.json、membership前端、membership.rs、services/membership-api、diagnostics.rs。

验收：授权目录预览正常，未授权目录被拒；会员六类状态与预期一致；无权限不创建处理任务；诊断中密钥明文命中为零。真实账号验收需用户已授权的测试账号，不绕过会员规则。

## 12. G08：安装包能交给没有开发环境的人使用

**目标：** 同一份安装包可追溯、可安装、可运行、可卸载。

1. 先关闭44项验收中的P0/P1及必需项阻塞，再使用现有准备与验证脚本打包；不把旧安装包冒充当前源码的结果。
2. 记录应用版本、Git提交、构建时间、包大小、SHA256、FFmpeg版本和许可证说明，保持package.json、Cargo与Tauri版本一致。
3. 在没有Node、Rust、FFmpeg和源码的独立Windows环境，用普通用户完成安装、首次引导、账号/API配置、导入、最短导出、结果预览和打开目录。
4. 验证路径含中文、输出不可写、断网启动、GPU编码不可用、升级安装、卸载再安装；卸载不删除用户选定的素材和成片。
5. 对外公开发布前处理现有清单中的代码签名、正式协议等事项。证书是否降低SmartScreen提示还受信誉机制影响，不承诺签名后完全无警告。自动更新另列设计，含签名验证与失败回滚，不临时拼接上线。

涉及：tasks/安装包发布准备清单.md、check-installer-readiness.ps1、scripts/verify-user-test-package.ps1、tauri.conf.json与发布说明。

验收：主44项无待验收的必需项，P0/P1为零；Windows10/11在声明支持范围内各一份干净环境报告；至少一次卸载保留素材检查。缺少第二种环境时明确限制测试包支持范围，不宣称全部兼容。

## 13. G09：以后每次改动都更小、更容易验证

**目标：** 降低牵一发动全身的概率，保留用户已验收行为。

1. 先为信息流模板排序、文件夹选材、输出参数转换和快照恢复补少量关键契约测试，避免写只复述实现的测试。
2. 第一次只把 App.vue 信息流编排迁至 `src/features/commerce-remix/` 的 composable/service，组件表现与接口不变，完整验收后再选择下一模块。
3. 再按职责拆分mix.rs，例如输入准备、效果组装、编码输出、输出验证；不为达成行数目标机械拆文件。
4. 建立一条本地统一检查入口，串起前端构建、Rust格式/check/clippy/test、会员测试与差异检查。条件允许再接CI，不把增加云服务作为前置。

验收：迁移模块行为、参数协议、基准样例输出保持等价；App.vue不再保留该模块完整业务实现；统一检查失败返回非零退出码；旧有回归不减少。先测构建时长与测试成本，再决定是否按模块拆快慢检查。

## 14. G10：处理速度与成片质量按数据优化

**目标：** 找到真实瓶颈，而非先盲目增加线程或更换模型。

1. 固定机器、素材、输出规格与缓存状态，测导入、缩略图、分析、切片、导出分别耗时，记录CPU、内存、GPU和临时盘峰值。
2. 选择10条短视频、100条短视频和至少一条长视频三档；使用足够的现有测试素材，不能把复制同一小文件当成真实大规模性能证明。
3. 优先优化重复探测、重复缩略图、编码器探测缓存和并发上限；GPU不支持时提供可理解的回退，保证最终参数仍符合用户要求。
4. 单次只改一个主要因素，同机前后各测三次取中位数；固定选材结果，避免视频内容不同导致“提速”假象。
5. 成片质量分开评估：镜头相关性、字幕可读性、音量与音画同步；信息流模板可以提高可控性，不能保证平台流量、转化率或过审。

涉及：materials、analysisCache.ts、material_library.rs、video_engine/probe.rs、thumbnail.rs、output.rs、task_runtime.rs。

验收：必须先交基线；建议只对已确认瓶颈争取耗时降低20%，其他阶段退化不超过10%，内存与磁盘开销不超过已确认预算。达不到时保留更简单稳定的实现，不为完成指标降低画质或遗漏处理。

## 16. 统一验收与记录办法

素材：`E:\Workspace\测试素材库`。测试结果：`E:\Workspace\测试结果库\Project_03_本地短视频批量混剪工作台\日期_目标编号_验收`。

每次结果至少包含：Git提交或未提交差异标识、机器配置、素材清单及哈希、参数、执行步骤、预期/实际、成片路径、截图或日志、通过/失败/阻塞。录屏与媒体留在测试结果库，不提交Git。

涉及前端执行 `corepack pnpm build`；涉及Rust执行 `cargo fmt -- --check`、`cargo check`、`cargo clippy --all-targets -- -D warnings`、`cargo test`；通用 `git diff --check`。真实FFmpeg测试运行前先确认测试目录配置，不让临时结果散落系统用户目录。若修改含中文PowerShell脚本，保存UTF-8 BOM并用Windows PowerShell5.1实际检查。

质量检查分别证明不同事情：构建证明能编译；契约测试证明参数传递；实际视频证明处理生效；桌面操作证明交互可用；干净电脑证明交付可用。这五层不可互相替代。

失败项模板：

```text
编号：G03-取消-02
版本：Git提交/工作区差异标识
素材：完整路径与哈希
前提：有效会员，2条并发任务
步骤：开始导出 → 确认两进程处理 → 点击取消
预期：5秒内本批次处理停止，已成功文件保留，源素材不变
实际：填写观察值，不预填通过
证据：进程日志、输出路径、截图路径
修复范围：相关前端调用与任务运行模块
复验：同一素材、同一参数、同一流程
```
